Current state of mind

How I think data should be built — right now.

This is a living page, not a manifesto. It's where my thinking actually sits today on what a good data platform looks like and how I like to work.

Endurance sport changes slowly; so does a considered opinion on architecture. Expect this to update a few times a year, not a few times a week.

Last revised: 2026 · views are my own and deliberately opinionated

01The platform I'd build today

A layered lakehouse where the boundaries between layers are the boundaries that matter — access and debugging — not arbitrary lines.

IAM · analysts + consumers
Access layer
Curated views & marts
Read-only, scoped per use case, organised into separate catalog databases. The only layer anyone downstream ever touches. Consumers physically cannot reach core or raw.
IAM · data engineers
Core layer
dbt transformations
The engineering workspace. Incremental, partitioned, tested, documented. Where messy raw becomes trustworthy tables. If something's wrong here, it's a model problem — and you know that instantly because of where it lives.
IAM · service accounts only
Raw layer
Iceberg tables · CDC + connectors
Written by machines, read by machines. Append-only CDC from outbox tables and custom connectors, partitioned by ingestion time. No human has routine access — not even admins. Looking here is a break-glass event, not a workflow.
Spans every layer
Observability
Eyes on everything, always — governance and quality aren't optional, they're what keeps the platform trustworthy enough to stay vendor-agnostic.

source systems → raw → core → access → BI · analytics · AI agents

The reason to split a platform into layers isn't tidiness. It's two concrete things: access control and operational clarity. Each layer maps to exactly one IAM boundary, so permissions stop being a spreadsheet of exceptions. And when something breaks, the layer tells you where to look before you've read a single log line — raw means a source or connector, core means a transformation, access means a view or a consumer query.

02The metadata question

On semantic layers, and why I'd usually skip the paid one.

A semantic layer exists to translate a business question into correct SQL — to make sure "revenue" means the same thing in every tool. That's a real problem worth solving. But a proprietary semantic-layer API only earns its place when you don't control the thing doing the querying.

When the BI tool or the analytical agent is something I control, I'd rather keep semantic context as metadata-as-code alongside the dbt project — the manifest gives structure, a small set of metric YAML files gives business logic, and both get fed straight into whatever consumes them. Version-controlled, reviewable, no per-query cost, no lock-in. An LLM agent reads the manifest to understand the model and the metric definitions to understand the meaning, and generates correct SQL without a paid API in the path.

The catch is discipline: metadata is only worth anything if it's maintained. So it gets the same treatment as the models — reviewed on the way in, owned by someone, and explained (the why behind a definition, not just the what).

03Principles I keep coming back to

Not rules. Defaults I need a reason to break.

01 GitOps everything

Every pipeline change goes through version control and deploys the same way — Argo, IaC, reviewable diffs. If I can't see who changed what and roll it back, it isn't production.

02 Efficiency over elaboration

The best architecture is the simplest one that meets the requirement — not every company needs the same solution. But a well-built lakehouse is simple enough that it fits a huge portion of them; I reach for more complexity only when the data actually demands it.

03 Open source where control is worth it

Increasingly I lean toward open-source and self-hosted tooling — partly for the control, partly because it forces me to actually learn the core technology that's often running quietly behind some fancy paid UI. That, plus no vendor lock-in, makes the extra operational overhead worth it more often than not.

04 Ask everything up front, document it all after

I'd rather get uncomfortably detailed answers from stakeholders before I build anything than guess and iterate. It's not about dodging responsibility — it's so I can write precise documentation for every report and process I create, so that months later someone can tell who uses it, why it exists, and what breaks if it changes.

05 AI belongs inside the process, not bolted onto it

AI works best as a first-class part of how I build, not an add-on after the fact — agent instruction files checked into every repo, and dbt model descriptions written carefully enough that they double as the semantic layer an AI agent reads to actually understand the business.

04How I like to work

The industry rarely lets you work exactly like this — but I like to dream that someday it will.

Scoped, shippable increments. One layer, one phase, one runnable thing at a time — over a big-bang build that's half-broken for a month.

Measure twice, cut once. I'd rather turn a decision over a few times before committing than move fast and patch it later — even though speed is sometimes exactly what the situation calls for.

Own the thing end to end. The best work I've done came from long engagements where I also operated what I built — because operating something changes how you build the next one.

The POC is the easy part. I love nothing more than building a proof of concept with the newest tech and seeing what it could actually replace. What's harder than it should be is getting a company to adopt it — real change means changing process, not just bolting on a new tool, and that's the part organizations resist.

05The AI data engineer I'd want running with me

One of my actual priorities right now — not an afterthought bolted onto finished work, but something I build toward from the start.

The platform in the sections above is the foundation, and that part doesn't change. What's changing is that I now build everything with half an eye on whether an agent could pick it up later — descriptions, AGENTS.md, instruction files checked into every repo as I go, not written after the fact because someone asked for them. And there's one general skills repo sitting above all of it: the place an agent checks first, has something like this already been solved, and how — before it starts from scratch.

Every finished ticket becomes a skill, not just a closed ticket. When I build something, I write up what I actually did — the pattern, the edge cases, the questions I had to go chase down before I could even start. That write-up goes into the skills repo and into the repo's own AGENTS.md. It's the deliverable, not a nice-to-have afterward.

So the next similar request doesn't start from zero. A Jira ticket or a ClickUp card comes in that looks like something I've already solved — the agent should recognize it, pull the matching skill, and have a draft PR or at least a real suggestion waiting before I've opened the ticket myself.

And it should ask before I do. If a ticket is missing something obvious — which tables it touches, who owns the downstream report, what the rollback looks like — it leaves a comment asking the person who opened it. I'd rather that gap get caught on day one than have me find it three days into the work.

The judgment calls still land on my desk. A draft PR or a comment is a starting point, not a decision. Anything ambiguous, anything architectural, anything that needs an actual conversation with a stakeholder — that's still mine. The skill library just means the obvious ninety percent of a ticket stops eating my time.

How far this actually goes, I don't know yet — think of it as a second me that's still finding its feet. Give it a year, and this is probably the section of this page that's changed the most.
